## Launching a game

`app/src/launcher.ts` launches the table the way a frontend does: `VPinballX_BGFX64.exe -Ini <VPinballX.ini> -Play <table.vpx>`, then watches the process's windows every 250 ms until it ends.
The game starts when the "Visual Pinball Player" window appears (it takes the foreground back if needed, `onPlaying`); VPX has taken over when Windows says that window holds the foreground (`onForeground`, read on every pass: the cinematic launch's coil thump).
Closing that window shuts VPX down cleanly (exit code 0).
Ctrl+Shift+K stops a stuck game (polite close, then forced after 5 s).

**No screen ever shows the Windows desktop.**
The menu windows are no longer hidden during a game: they stay behind VPX's windows, without taking focus from it.
The playfield keeps the loading screen (the game's loading video, or a fallback screen; on a desktop, the controls panel) until the game window appears, then each screen switches to its **in-game background**: the game's media, frozen by default, visible only on a screen VPX does not use (topper without a window, backglass without a `.directb2s`, no DMD); see "Loading and play".
For this, each window receives a `game` state (table, media, playback of each role), rendered by `renderGame` (`app/renderer/frontend.js`).
On return, the menu takes the foreground back as before.

A single rule covers every moment, the **screen guard** (`app/src/screen-guard.ts`, started by `main.ts` before any other window, except the waiting screen for another running frontend):

- **one black cover per screen**, present from startup to shutdown, which follows screens being added, removed and rotated; it never takes focus (`focusable: false`) and only appears once painted black.
  It covers screens without a Cyber Pinball window: a screen with no role, and screens other than the main one with `--reglages`;
- **screen unplugged and plugged back in by Windows**, even during a game (a graphics card that detects its outputs again can do so every twenty seconds; seen during a game in the headset): Windows moves the windows of the vanishing screen to the main screen, and the screen comes back with another identifier.
  Its new cover goes at once under the Cyber Pinball windows (`tuckVeil`), never in front of the window of the screen's role; screen names in the reports follow their place, not their identifier.
  Outside a launch or a game, once the screens have settled, each menu window moved off its screen takes it back (`recoverScreens`, `recoverCovered` in `app/src/cover-display.ts`); during a launch or a game nothing moves (the foreground goes to VPX), and the recovery happens on return, at once then 1.5 s later.
  A cabinet screen left black under its cover (`veiledScreens`, `packages/core/src/screencover.ts`) is reported ("Écran « FullDMD » : resté noir sous son voile (retour d’une partie) ; la fenêtre du menu repasse devant.", FullDMD screen left black under its cover (return from a game); the menu window comes back in front), counted in the endurance report and written to the screens log;
- **gap-free relaunch** (`relaunchCovered`, the only way to relaunch the application: menu → wizard, wizard → menu, settings → wizard): the new process opens its covers and windows on top of the old one's, which only closes 400 ms after the new one has reported its windows painted (marker file `CYBERPINBALL_RELEVE`, created by `paintedOnScreen` in `app/src/offscreen.ts`; 15 s wait at most): being visible to Windows is not enough, since a window is transparent until its first frame;
- **never a light screen**: when a window appears, Windows 11 paints it in a light color before showing its page, even when already painted (`ready-to-show`) and despite `backgroundColor`.
  Two distinct flashes, measured on real screens (a probe reading the screen every 8 ms): the light theme's system backdrop (#F3F3F3, "Mica"), as long as the window has received no frame, always for the process's first window and for one to three seconds when the menu starts, on all four screens; and a pale blue fill (#D3E3FD) of about 25 ms each time a window appears already full screen (shown, or restored from the taskbar).
  `createWindow` therefore creates every window without a system backdrop (`backgroundMaterial: 'none'`): before its first frame, it lets what it covers show through (the black cover).
  And `coverDisplay` only makes a window full screen once it is shown: not yet shown, it takes the size of its screen and goes full screen when it appears; `minimizeCovered` ("Bureau Windows", Windows desktop) leaves full screen before minimizing it.
  Tried without enough effect: DWM transitions disabled, Electron's dark theme (gray #202020), appearing transparent then opaque (`setOpacity`: while transparent, the window does not present its frames to Windows, and the flash comes back when it turns opaque);
- **taskbars hidden during a game**: when VPX takes the foreground, before its game window goes full screen, Windows briefly brings the taskbar back in front of the screens it does not occupy (seen on the DMD screen).
  They come back at the end of the game, when the application closes, and at the next startup if the application stopped in the middle of a game (marker `barres-des-taches-masquees` in the data folder): only the ones Cyber Pinball hid, a taskbar already hidden by another frontend stays hidden;
- **taskbars always behind the menu** (taskbar guard, `packages/core/src/taskbarguard.ts`): Explorer only puts a screen's taskbar behind a full-screen window when that window takes the foreground, and brings it back in front as soon as another window takes it or the taskbar is shown again.
  At startup, each menu window takes the foreground as it appears; after a game, only the playfield takes it back, and the DMD and backglass never have it: their taskbar, shown again, stayed in front (at times on the DMD, sometimes on the playfield).
  Now each taskbar is put under the menu window of its screen before being shown again (`placeWindowBelow`, without activating anything), then the taskbar guard runs again when coming back from a game, from the desktop, at every screen or work area change, every time a menu window takes the foreground back, and at every screen guard check: a taskbar in front of a menu window is put back behind (« Barre des tâches (Shell_SecondaryTrayWnd) devant « Cyber Pinball — DMD » sur l’écran « DMD » (retour d’une partie) : remise derrière. »).
  Never while another program has the foreground (VPX in game, Start menu).
  A taskbar that Windows brings back in front five times within ten seconds is hidden as during a game, with the same marker, until desktop mode or until the application closes.
  Nothing is set in Windows: only the window order changes, as Explorer does itself;
- **screens log** (`<data>\logs\ecrans.txt`, 512 KB at most, oldest entries removed): at every switch (menu startup, game start, VPX game window shown, back from a game, Windows desktop and back, screen change, taskbar put back behind), the Windows foreground window, for each cabinet screen the Cyber Pinball window that covers it and everything above it (« BARRE DES TÂCHES DEVANT », taskbar in front; « DÉCOUVERT », uncovered), and the rectangle of each taskbar, shown or hidden, permanently on top or not.
  "Santé de la borne" (Cabinet health), "Écrans" (Screens) group, says how many times the guard put a taskbar back behind since startup, and flags as to check a taskbar it had to hide;
- **console report**: twice a second, the Windows window stack is read again (`screenCover`, `packages/core/src/screencover.ts`); a screen that stays for more than a second without a Cyber Pinball window covering it, or under a taskbar, produces "Écran « Topper » : aucune fenêtre de Cyber Pinball ne le couvre, le bureau Windows se voit." (Screen "Topper": no Cyber Pinball window covers it, the Windows desktop shows through.), then "de nouveau couvert" (covered again).
  The endurance test counts these reports per launch ("écrans découverts" (uncovered screens)).
  "Bureau Windows" (Windows desktop) in the system menu suspends the rule until you return;
- **desktop mode**, the reverse rule (`app/src/desktop-mode.ts`, system menu > "Borne" (Cabinet) > "Bureau Windows" (Windows desktop) or Ctrl+Shift+D): every screen of the PC becomes usable again, however many there are.
  Every application window leaves its screen, whatever it is (`BrowserWindow.getAllWindows`): the menu windows are minimized, the black covers hidden (`hideCovered`, taken out of full screen first so they do not come back pale blue), and taskbars a game may have left hidden come back.
  Every page of the application is muted until the return (`DesktopContents`), juke-box included.
  Without this, often only one screen came back, because only the menu windows were minimized and the covers, which have no taskbar button, stayed full screen on every screen.
  On the desktop, twice a second, a Cyber Pinball window back on a screen (cover of a screen plugged in meanwhile, reopened window) is put away again ("Mode bureau : « … » était revenue sur son écran, de nouveau rangée." (Desktop mode: "…" was back on its screen, put away again.)), and the guard reports a screen still covered, even partly ("Mode bureau : écran « Topper » encore couvert par « … »." (Desktop mode: screen "Topper" still covered by "…".), `desktopBlockers`).
  Ctrl+Shift+D becomes a global shortcut for the duration of desktop mode (released on return; if another program already holds it, the console says so and the taskbar remains the way back).
  **Cabinet "Bureau Windows" (Windows desktop) button** (interface buttons, optional, `navigation.desktop`, no keyboard fallback): in one press, from any menu screen, it does what Ctrl+Shift+D does (`handleKey`, guest-mode door `shortcut.desktop`).
  As a joystick button, it is watched on the desktop (`watchDesktopButton`, `app/src/start-relaunch.ts`): released then pressed again, it brings back the menu, except during a VPX game started from the desktop.
  As a keyboard key, it is not read on the desktop (a global shortcut without Ctrl would take that key from all of Windows): Ctrl+Shift+D, the taskbar or holding Start then bring back the menu.
  The cheat sheet and the "Bureau Windows" entry name this button.
  On return, each screen first gets its cover back (a screen plugged in during desktop mode gets its own), then the windows put away come back in front of it, and the playfield takes the foreground again.
  **You come back where you were** (16/11/2026): desktop mode no longer closes the open screen ("Borne" (Cabinet) section on "Bureau Windows" (Windows desktop), 3D vision, a table's page…), which waits as it is; before, the return always went to the wheel.
  A relaunch on return (quarter turn of the screen) takes it back too (see screen orientation).
  **Ctrl and Shift in a shortcut do nothing on their own** (`packages/core/src/modifier-chords.ts`): on a keyboard, left Ctrl is the left MagnaSave (previous collection on the wheel) and left Shift the left flipper, and Ctrl+Shift+D changed collection or moved up a line before opening the desktop.
  In the menu windows, a modifier key press waits 300 ms (`CHORD_HOLD_MS`): released before, it acts on release; held, it acts at the end of the delay then repeats as before; followed by a Cyber Pinball shortcut (Ctrl+Shift+D, Ctrl+Shift+K, Ctrl+Q, `isAppShortcut`), neither its press nor its release acts; followed by another key, it acts just before it.
  Modifiers held together (guest-mode unlock combination) all arrive, in order, at the end of the delay.
  Joystick buttons, the phone and the headset controllers do not go through it.
  A D key held on return does not send back to the desktop (repeat ignored).
  Tests: `packages/core/src/test/bureau-reprise.test.ts`.
- **complete shutdown, single instance** (`app/src/app-lifetime.ts`, `app/src/single-instance.ts`, rules in `packages/core/src/lifetime.ts`): a menu or wizard window closed from Windows (Cyber Pinball's taskbar button, Alt+F4) closes the whole application, its other windows and covers included, as does the last window with a taskbar button (VPX settings on their own).
  Before, only the playfield closed: the backglass, DMD, topper and covers stayed open, invisible in desktop mode, and "Cyber Pinball" processes stayed in the Task Manager (reported on 08/11/2026).
  Guest mode still refuses Alt+F4.
  A requested shutdown that does not complete is forced after 15 s ("Fermeture : Cyber Pinball tourne encore 15 s après la demande (…) ; sortie forcée." (Shutdown: Cyber Pinball still running 15 s after the request (…); forced exit.), with the windows left open).
  A second launch does not start next to the first: the open instance leaves desktop mode or takes the foreground again (not during a game), and the second launch closes; it waits up to 8 s for an instance that is closing (dedicated cabinet relaunch, double-click right after quitting).
  The lock is Electron's, tied to the profile: each test sandbox has its own; the new process of a handover starts at once and takes the lock once the old one has exited.
  Tests: `packages/core/src/test/fermeture-complete.test.ts`.

Tests pin down the rule: no window is hidden with `hide()` (except the covers, through `hideCovered`, in desktop mode only), the application only relaunches through `relaunchCovered`, and the guard starts before the other windows (`packages/core/src/test/screencover.test.ts`); every window is created without a system backdrop, and full screen and minimizing only go through `cover-display.ts` (`packages/core/src/test/offscreen.test.ts`); in desktop mode, with the simulated screens of `packages\core\ecrans-simules` (1 to 4 screens), no Cyber Pinball window covers anything any more, then every screen is covered again on return, its cover put back before its window (`packages/core/src/test/mode-bureau.test.ts`).

**No editor or audit window.**
With `-Play`, VPX 10.8.1 does not create its editor (`PlayTableCommand`, `src/core/AppCommands.cpp`): no table audit (the "Table audit" box only exists in the editor, when opening a table with errors), no script editor (a script error goes to the log and to an in-game notification), no progress window, debugger or table picker.
Checked on the development PC with three tables, including Terminator 2 1.25, whose audit reports 18 errors: only the "Visual Pinball Player", "Visual Pinball Backglass" and "Visual Pinball Score View" windows (class `SDL_app`) are shown; "Visual Pinball Topper" is created hidden when the topper is not assigned; nothing more on exit.

Two VPinballX.ini settings still make VPX ask a question in the middle of loading; Cyber Pinball manages them (written at every sync, with manual changes detected and never silently overwritten, like the other managed keys):

| Setting | Value written | Otherwise |
| --- | --- | --- |
| `[Player] SecurityLevel` | `0`: all ActiveX objects in the script allowed (VPX default) | from 1 to 3, "This table is attempting to create an object of type …" (Yes / No) for each object, even `Scripting.Dictionary`; at 4, all refused and the script stops |
| `[PlayerVR] AskToTurnOn` | `2`: VR off (VPX default); a game in VR has its own INI ("Virtual reality", below) | at 0, "Connection to VR headset failed / Retry connection ?" (Yes / No) or "VR mode activated but OpenXR initialization failed."; the Windows build of VPX includes OpenXR |

Every other visible VPX window is classified (`classifyVpxWindow`, `packages/core/src/vpxwindows.ts`):

- **dialog box** (`#32770`): the game stops and its text becomes the on-screen message, without the buttons.
  The ActiveX prompt and the VR headset prompt are recognized: the message names the setting to restore.
  The text is read with `WM_GETTEXT` (`windowControls`): it is the only way to read an edit box in another process, where VPX puts the audit report and script errors;
- **table options form**: a box with at least one checkbox or radio button, and an OK button (or a single push button).
  It is the one `core.vbs` builds with `VPinMAME.WSHDlg` (`cvpmDips`) when a table offers its options at startup, for example "TABLE OPTIONS MENU" in the VPW Addams Family.
  It only appears when VPinMAME is registered in Windows, often on a cabinet that comes from another frontend.
  Nobody can answer it on a cabinet without a mouse: Cyber Pinball presses its OK (`pressDialogButton`, posted `WM_COMMAND`), like a click, and the game goes on with the choices the table already saved.
  If the box is still there 3 s later, the game stops as for an error.
  Before 12/11/2026 it stopped the game, and the table asked again at every launch: it could never be played;
- **editor window**, if another version of VPX opened one: the editor (class `VPinball`), the script editor (`CVFrame`), "Preparing Table" and the debugger are hidden (closing them would quit VPX or ask a question), the table audit ("Dialog" box whose text starts with "Table audit:" or "This table contains error(s)") is closed; the game goes on, and the game window takes the foreground back;
- **unknown window**: left on screen.

The options form and the last two cases leave a one-sentence report (`LaunchResult.notices`): written to the console at the end of the game, added to the message of a failed game and to the endurance test summary ("autres fenêtres de VPX" (other VPX windows)).

**Script written for an older core.vbs.**
*Back to the Future (Data East 1990)* stopped at every launch on "Table script bug: cvpmFlips2.Init is called twice.
Maybe 'vpmInit Me' is duplicated in the code ?": its script calls `vpmInit Me` twice in `bttf_Init`.
Older core.vbs versions let it through (a second `vpmInit` does nothing more: events already created, same PinMAME settings); the one in VPX 10.8.1-5436 (`cvpmFlips2.Init`) shows that message and quits the game (`QuitPlayer 2`).
The scripts VPX provides to tables thus refuse slips of older tables: each known case is a rule in [scriptcompat.ts](../../packages/core/src/scriptcompat.ts), which spots it in the script's text (without VPX), fixes it without moving a line, and recognises the message VPX stops on.
For `vpmInit`: from two calls in the code on (comments, strings, `object.vpmInit` and a `vpmInit` defined by the script left out), Cyber Pinball's `.vbs` (`scriptpatch.ts`, as for PuP-Packs) replaces each call with `CyberPinball_VpmInit`, defined after the last line, which calls `vpmInit` only the first time; its last line keeps `"compat": ["vpmInitOnce"]`, which the other `.vbs` repairs (PuP-Pack, updated table) keep.
The table is not modified; a `.vbs` from elsewhere is fixed itself.
Doctor finding "Script écrit pour un ancien core.vbs" (Script written for an older core.vbs) (`scriptCoreCompat`), repaired at installation and before each game (`PUP_PLAY_REPAIRS`); script readings move to version 8, so tables already installed are read again.
When the text shows nothing (a single `vpmInit`, in a Sub called twice), the game stopped by that message gets the `.vbs` fixed right away (`repairScriptAfterStop`), and the failure screen says "Cyber Pinball a corrigé le script de la table (…) : relancez-la." (Cyber Pinball fixed the table's script (…): start it again.).
**VR room drawn without the headset** (`vrRoomOnScreens`): a VR version of a table turns on its room (cabinet, room, 3D backglass) through a switch in its script; a hybrid table keeps it for the headset ("If RenderingMode = 2 or VRTest = 1"), but a version made for the headset only turns it on outright ("Const VR_Room = 1"), and a test switch left at 1 (`VRTest`, `LiveViewVRSim`) turns it on even in a hybrid table.
On the screens, VPX then draws the whole room every frame although it is only of use in the headset.
The rule spots these switches turned on outside any Sub (`VR_FLAG`), and Cyber Pinball's `.vbs` multiplies their value by `Abs(RenderingMode = 2)`, which is 1 in VR and 0 on the screens, on the same line (a `Const` becomes a variable).
The doctor says so on the table's page ("Pièce VR dessinée hors du casque" (VR room drawn without the headset), action "Réserver la pièce VR au casque" (Keep the VR room for the headset)) and repairs it before every game; a protected script cannot be fixed: the finding advises the non-VR version, or the switch set to 0 in the VPX editor.
Tests: `vr-hors-casque.test.ts`.
Tests: `scriptcompat.test.ts` (detection, lines in place, run by `cscript` on a fake core.vbs: a single call to `vpmInit`, doctor, PuP-Pack, updated table, `.vbs` from elsewhere, stop message) and the `scriptCoreCompat` trap table.

`node scripts/sonde-fenetres.mjs --exe … --ini … --table …` (after `npm run build`) lists every window of a game, hidden ones included, along with what the launcher would do with them; `--commande Edit` opens the table in the editor to check that the editor and the audit are recognized on real windows.
Always on copies of the table and of VPinballX.ini.

**DMD set for desktop mode.**
A table that picks its DMD with a VPX menu option set by default for desktop mode (*JP's Space Cadet* v7.0: "DMD Type" on "Desktop DMD") left the DMD window black on a cabinet.
On a cabinet with a DMD screen or zone, that option is switched to FlexDMD in the table's `.ini`, at installation and before each game (`PUP_PLAY_REPAIRS`), without overwriting a choice made in the VPX menu: see [DMD set for desktop mode](vpx-plugins-backglass-pup-and-dmd.md#dmd-set-for-desktop-mode).

**ROM volume before and after the game.**
Just before the game, Cyber Pinball sets the wanted volume in the ROM's memory (the player's choice, or the recommended volume instead of a low factory volume); afterwards, a volume changed at the coin door becomes the player's choice.
Never during the game, nor in the double of a game between friends (the table copy used for that game), nor for "Régler l'affichage en partie" (Adjust the display during a game): see [ROM volume](sound.md#rom-volume).

**Frame rate of every game.**
A sluggish table left no trace: neither VPX's log nor the reports said how many frames per second the game held (11/17/2026: tables brought over from another installation were sluggish on one cabinet and not on another).
The "CyberPinballDmd" VPX plugin, enabled in every game (see [DMD position during a game](vpx-plugins-backglass-pup-and-dmd.md#dmd-position-during-a-game)), now counts the rendered frames (`VPXPI_EVT_ON_PREPARE_FRAME`, [cadence.h](../../packages/vpx-vision3d/src/cadence.h)) and puts the gap between two frames in a histogram to the millisecond; the first 5 seconds (table preparation, first videos) do not count.

- **In `vpinball.log`**: each stall (at least 100 ms between two frames) when it happens ("Cadence: stall of … ms at …s", the first 30), then a summary every minute and at the end of the game: `Cadence end: frames=… duration=…s fps=… p50=…ms p95=…ms p99=…ms max=…ms late=…% stalls=… worst10s=…fps mem=…MB`.
  That is the frames per second, the median and the 95th and 99th percentiles of the gap, the longest gap, the share of late frames (more than 1.5 times the median), the stalls, the worst 10 s window and VPX's private memory; a `Cadence running` summary is an interim one.
- **Read back after the game** (`noteGameCadence`, [app/src/game-cadence.ts](../../app/src/game-cadence.ts); parsing in [vpxcadence.ts](../../packages/core/src/vpxcadence.ts)): only what VPX wrote during this game; the end summary, otherwise the last interim one (VPX stopped before the end, crash).
  The target frame rate is read at launch ("Synchronization mode: … with maximum FPS: …, display FPS: …": the smaller of the two; 60 if the line is missing).
- **In the cabinet log**, one line in French: "Cadence de la partie (…) : tenue — … images/s pour … visées, médiane … ms, …", followed by the 99th percentile, the longest gap, the share of late frames, the stalls, the worst 10 s window, VPX's memory and the measured duration.
  The verdict there is "tenue" (kept up), "RAME" (sluggish), "À-COUPS" (stutters), "RAME, avec des à-coups" (sluggish, with stutters) or "trop courte pour juger" (too short to judge); with no summary (plugin missing, game too short), the line says so.
  Every cabinet report contains this log and VPX's log of the last game (see [Tech sheet](tech-sheet.md#tech-sheet)).
- **Verdict** (`cadenceVerdict`): the game is sluggish if its average is under 90 % of the target, its worst 10 s window under 75 %, or if at least 10 % of the frames are late; it stutters from 3 stalls and at least one per minute; under 20 s of measured play, it is too short to judge.
- **Record per table** (`recordGameCadence`): each judged game goes into `<données>\logs\cadence-parties.json` (the last 3 per table, 400 tables at most, the most recently played; atomic write), a game in the headset marked as such.
  The doctor reads it to say that a table is sluggish on this cabinet (see [Cabinet health](cabinet-health.md#cabinet-health)).
- **Bench and tests**: `scripts/banc-cadence.ps1` (the real VPX on the hidden desktop, the same table played with backglass and DMD windows of several sizes), `packages/vpx-vision3d/test/banc-cadence.cpp` (the counter alone), [cadence-partie.test.ts](../../packages/core/src/test/cadence-partie.test.ts) (summary read field by field, same format written by the plugin and read by Cyber Pinball, target frame rate, verdict, log line) and the `slowTable` trap in [doctor-traps.test.ts](../../packages/core/src/test/doctor-traps.test.ts).

### Virtual reality

System menu > "Borne" (Cabinet) > "Réalité virtuelle" (Virtual reality) > "Réalité virtuelle" (Virtual reality) (`app/src/vr.ts`, rules in `packages/core/src/vr.ts`): off by default, Start toggles it.
The entry carries a "BETA" badge in all its states, as the feature is still being tested: a pill after the label (`badge: 'beta'`, `MenuBadge` type in `app/src/library.ts`, reusable by any menu entry; `LigneMenu` component of the design system).
The entry reads the active OpenXR runtime without waking the headset: the `XR_RUNTIME_JSON` variable, otherwise `HKLM\SOFTWARE\Khronos\OpenXR\1`, value `ActiveRuntime` (`packages/win-displays/src/openxr.ts`), written by Meta Quest Link, SteamVR or Virtual Desktop.
Its detail names the runtime; with no runtime, or if its manifest is gone, the entry stays visible, greyed out, with the reason.
The choice is kept in `<données>\vr\reglage.json`.

When it is on, each game (not "Régler l'affichage en partie" (Adjust display in game)) gets its own VPinballX.ini, `<données>\vr\VPinballX.ini`, or the double of a game with friends, rewritten in place.
It is a copy of the cabinet's, which keeps `[PlayerVR] AskToTurnOn = 2`, with:

- `[PlayerVR] AskToTurnOn = 1` ("Autodetect"): VPX 10.8.1 plays in the headset if the runtime answers and the headset is ready, otherwise on the screens, without any question (`Player::Player`).
  The value 0 is never written: without a headset, it would block the cabinet on "Retry connection ?";
- `[PlayerVR] AddBackglass`: at 1, VPX places a panel above the playfield that shows what the backglass window would draw (B2S and PUP plugins).
  At 0 for a table that has its own VR room, and so its own backglass already: it is recognised by its script (`tableHasVrRoom`: `RenderingMode = 2`, a `VRRoom` or `VR_Room` option, or at least three `VR_…` objects, comments left out; 7 tables out of 11 on the development PC);
- `[PlayerVR] PreviewDisplay` and `PreviewFullScreen` (`vrPreviewSettings`): the preview of what the headset sees takes the place of the game window, which does not exist in VR: playfield screen (`[Player] PlayfieldDisplay`) and same mode (`PlayfieldFullScreen`, full screen or windowed).
  The backglass, DMD and topper keep their windows in VR (VPX log of 9 November 2026): putting the preview there would stack them.
  Without this setting, VPX opens a square window in the middle of the main screen.
  Nothing is written when the cabinet's VPinballX.ini already picks the preview screen.
  Worked out again for every game: a screen plugged back in changes its name.
  If VPX mixes up two screens with the same name, the window is brought back onto the playfield screen during the game (`VPX_ANCILLARY_WINDOWS`);
- the VR settings of the previous game: the `[PlayerVR]` section (table orientation and position, which VPX saves when it quits, `LockFeetToGround`…), except the preview screen, and `[Player] VRPreview`.
  After a game with friends, they are taken from the double before it goes (`rememberVrSettings`).

In VR, VPX does not open "Visual Pinball Player", but "Visual Pinball VR Preview" (what one eye sees).
It also creates the backglass, DMD and topper windows, but hidden, and never shows them in VR (their rendering is skipped: "Ancillary windows are not yet supported while in VR mode"): those screens keep the Cyber Pinball background.
The game's INI therefore keeps the cabinet's outputs (`[Backglass] BackglassOutput`, `[ScoreView] ScoreViewOutput`, `[Topper] TopperOutput`, `ANCILLARY_OUTPUTS`): with the headset not ready, the game is played on the screens with that same INI, and the backglass, DMD and topper must be there (on 12 November 2026 they were turned off: the voices of the Aliens PuP-Pack without any video).
A game fallen back to the screens without one of them is reported in the log (`screensFallbackGaps`).
The backglass in the headset does not depend on them: VPX draws it through the plugins, whatever the window mode.
VPX 10.8.1 freezes when quitting a game in the headset (three games out of three on 9 November 2026, nothing in its log after the last frame): when Windows declares the preview hung (5 s without responding) and it stays so 3 s more, after at least 20 s of play, Cyber Pinball closes it (`isHung`); exit code 0xCFFFFFFF ("Close the program" chosen in Windows' "not responding" window, `VPX_HUNG_EXIT_CODE`) is no longer taken as a failed game.
The launcher takes the preview as the game window (`LaunchResult.vr`), and the log says "partie dans le casque" (game in the headset) or "casque pas prêt, partie sur les écrans" (headset not ready, game on the screens).
**One pose, fixed.**
The place of the headset cabinet (`<données>\vr\casque.json`) is the only one: for every game in the headset it is written into the game's INI (`placeVpxSettings`: `[PlayerVR] Orientation`, `TableX`, `TableY`, `TableZ`, and the lockbar if the cabinet is aligned), so the VPX table is exactly where the menu cabinet was.
Nothing moves it by itself: neither the companion (in the Quest room, a space change announced by the Quest is only reported) nor Cyber Pinball.
It only moves on request: "Caler la borne" (Align the cabinet), or keypad 5 (at the menu, the cabinet comes in front of the player; in game, VPX recentres the table for that game only).
Only if nothing gives a place (neither casque.json nor a place saved by VPX, `vrHasSavedPlace`) would the table be put at the origin of the headset space, often around the player; Cyber Pinball then waits for "Startup done" in `vpinball.log`, and presses VPX's recentring key for it, if VPX has the foreground (`VRCenter`, keypad 5: `vrCenterKey`, `centerWhenStarted`): the table comes in front of the player, lockbar at `[Player] LockbarHeight` (85 cm by default).
Keypad 5 recentres it by hand, 8 and 2 raise and lower it; VPX keeps this place when it quits.
During a game in the headset, both MagnaSave buttons open the VPX menu directly (its key, F12 by default), which shows in the headset: its "Virtual Reality Settings" page recentres and moves the table.
The Cyber Pinball menu, on the screens, would not be seen there.
The VPX menu is drawn in the headset only, over the picture of both eyes ("LiveUI" pass after `ApplyStereo`, `Renderer.cpp`): the preview does not show it.
Closing the preview window stops the game like Escape (`SDL_EVENT_WINDOW_CLOSE_REQUESTED`, `CS_STOP_PLAY`): with `-Play`, VPX saves the VR settings and closes, and Cyber Pinball goes back to the menu as after any game.

**Load during the game.**
During a game, in the headset or not, the menu stays at rest: its windows keep a still image behind VPX, the headset companion has stopped after handing over, and its screens rendered off screen are closed.
To check it on the cabinet, every 5 s the menu reads what its processes take (`app.getAppMetrics`: main, Chromium GPU, screen pages, others) and what VPX takes (`GetProcessTimes`, `processCpuMs` in `packages/win-displays/src/processes.ts`), as a percentage of one core, without starting or waking anything; at the end, a log line sums it up ("Charge pendant la partie (dans le casque) : Cyber Pinball 1,2 % d’un cœur en moyenne, 3 % au plus (principal 0,4 %, GPU de Chromium 0,3 %…) ; VPX 95 % d’un cœur en moyenne…", Load during the game (in the headset): Cyber Pinball 1.2% of one core on average, 3% at most (main 0.4%, Chromium GPU 0.3%…); VPX 95% of one core on average…).
It is used to compare before and after a change (Link settings, driver, VPX version).
Code: `app/src/game-load.ts`, `packages/core/src/game-load.ts`, test [game-load.test.ts](../../packages/core/src/test/game-load.test.ts).

Limits: the Cyber Pinball menu stays on the screens (Virtual Desktop shows the desktop in the headset); no DMD in the headset for a table without a VR room (VPX only adds the backglass there, and its plugins cannot place an object in the scene); a setting other than the VR ones, changed during a game in the headset, is kept only if it is saved for the table ("Réglages de VPX" (VPX settings) sets the others for all games).
Tests: `packages/core/src/test/vr.test.ts`.

#### Menu in the headset

With virtual reality on and the headset ready, the Cyber Pinball menu also shows in the headset, laid out as a cabinet: the playfield lying in front of the player, tilted by 6.5°, the flipper edge towards them, the lockbar 85 cm above the floor; at the far end of the playfield, upright, the DMD (or FullDMD), the backglass above it, then the topper.
On a real aligned cabinet, each screen keeps its real size (EDID or size entered in the wizard; otherwise a default width).
At a desk, or without an aligned cabinet, the head takes a cabinet's proportions (`STANDARD_HEAD`): the backglass slightly wider than the playfield (1.05 times), the DMD half as wide as the backglass (a quarter of its area), centred below, the topper very small (0.4 times the backglass), sitting on it; each keeps its picture's proportions.
In every case, the playfield at least that of a 42-inch cabinet (`MIN_PLAYFIELD_M`, 93 cm: a 17-inch desktop playfield would make a toy cabinet).
You navigate with the cabinet buttons as usual: the screens do not change, and Cyber Pinball keeps the foreground.

The menu is drawn separately for the headset (`app/src/casque-vues.ts`): one Cyber Pinball window rendered off screen per cabinet screen, the same page as on the screens, the playfield in the cabinet layout (portrait), whatever the PC screen, which keeps its menu in landscape.
Windows shrinks a window, even a hidden one, to the work area of the main screen (1920 × 1032 on a 1080 screen): the page keeps its screen's proportions and a zoom gives it its layout (`headsetViewSize`).
Their pictures are GPU textures (`webPreferences.offscreen.useSharedTexture`): their NT HANDLE is duplicated into the companion (`openHandleTarget`, `packages/win-displays/src/handles.ts`), a new one for every picture (Electron opens one per picture and Windows recycles their numbers), and Electron takes its texture back when the companion answers "libre".
These windows hear nothing, receive no button, and what they send on their own is ignored (`isHeadsetView`).
The native companion `cyberpinball-casque.exe` (`packages/casque-vr`, C++, Direct3D 11 and OpenXR) shows each picture as an OpenXR panel ("quad" layer); without those windows, it duplicates the PC screens (DXGI desktop duplication).
It opens no window.
Switching between the PC and the headset: with the headset on, the menu is drawn for it alone, and the PC screens rest ("Dans le casque" (In the headset), nothing else to draw); taken off, or the Meta menu open (OpenXR session no longer "FOCUSED", "porte 0"), nothing is rendered for the headset any more, but the PC screens stay on "Dans le casque": no back and forth every time the headset is lifted.
They only take the menu back when the headset is switched off or Link is cut (see below).
The OpenXR loader is `openxr_loader64.dll` from the VPX copy, loaded at run time: nothing is installed in Windows.
Cyber Pinball (`app/src/casque.ts`) starts it when virtual reality is on and the runtime is present, describes the panels to it (`packages/core/src/casque.ts`, `headsetPanels`, one line per screen on its standard input), and starts it again every 15 s while the headset is not ready.
Before a game, Cyber Pinball hands over to it ("releve"): it keeps the headset, loading screen included, until VPX takes the player's gaze (its OpenXR session is no longer "FOCUSED"), then stands by, drawing nothing ("releve … veille"); never the Meta home between the menu and the table.
When the game ends, the companion starts a fresh session (`HeadsetMenu.restart`): a fresh session takes the headset by itself (about 1 s), whereas the session standing by waited for the player to pick it again in the Link home (5 to 11 s, test of 10 November 2026).
A session stopped by the runtime ("session-arretee": Link home, application picked again) starts a fresh session at once; it is not a lost headset.
Two minutes at most if VPX does not take the headset; game on the screens (headset not ready for VPX): stopped at once.
In the headset, the playfield is in portrait, as on a cabinet, even with a landscape PC screen: its page rendered for the headset is turned a quarter (`headsetTurn`) and takes the cabinet layout.
Once per startup, a few seconds after the first pictures, the companion saves each panel's picture as it sends it to the headset (`<données>\logs\casque\<role>.bmp`): a defect seen in the headset can be compared with it.
The cabinet stays where it is in the room, like an object: its floor position and heading are kept in `<données>\vr\casque.json` and given back to the companion at each start ("ancre"), after a game as at the next startup.
Without a kept place, it settles in front of the player at the first gaze the headset really tracks ("TRACKED" position and orientation: lying down or not worn yet, the headset only gives a frozen pose).
Keypad 5 (VPX's recentring key) and the headset's recentring (Meta button held) bring it back in front of the player.
A screen is only copied to the headset when its picture changes (a pointer move alone does not count): a still menu costs nothing to the GPU or to Link.
**Smoothness** (test of 10 November 2026: "it moves a little too much, it is not very smooth"): the companion's frame loop never waits for the GPU any more; each copied Electron texture is given back ("libre") when an event query issued after the copy has completed, read without waiting on every turn (before, `gpuFinish` waited there for all the GPU work, mipmaps included, on every picture received, enough to miss headset frames and let its reprojection make the screens shake).
With the headset on, the companion logs its cadence every 10 s: headset frequency, frames per second, skipped frames (gap between predicted display times), longest copy and render, pictures received ("cadence casque …").
The scene never moves by itself: no animated halo, nothing else.
**Stable screens whatever the frame rate** (test of 10 November 2026: "it makes you feel a bit sick" when turning the head).
Measured: 14 to 56 frames/s from the companion for 72 Hz ("cadence casque"), and, in Oculus's performance log, 147 to 1,359 application frames per minute for 4,320 expected, 291 to 519 PC frames lost per minute, most with a loaded CPU, ASW on ("ASW Enabled") over a Link cable.
The pose chain was right (`xrWaitFrame`, then `xrLocateViews` at `predictedDisplayTime`, the rendering, and `xrEndFrame` at that same time, everything laid in STAGE), but the screens were drawn in the projection layer, without depth: each late frame was shown again with the head rotation only, and screens one metre away slid as soon as it moved sideways.
Outside alignment, the screens are therefore "quad" layers laid in the room: the runtime composes them again at every headset frame, at their exact place, whatever the companion's frame rate.
The projection layer (the rest of the scene, and the screens during alignment, where the tip of the controllers passes in front) is submitted with its depth (XR_KHR_composition_layer_depth, near 5 cm and far 50 m like the projection: `NEAR_Z`, `FAR_Z`); at launch the companion says "profondeur soumise au runtime" (depth submitted to the runtime), or why it is not.

**Graphics profile of games depending on the machine** (`packages/core/src/vr-profil.ts`).
The companion reports the graphics card driving the headset ("carte <MB> batterie|secteur <name>", card MB battery|mains name, kept in `<données>\vr\carte.json`).
The profile is chosen on general criteria, never on a model name (`vrGraphicsProfile`):
- **puissant** (powerful): 10 GB of video memory or more, desktop machine (a cabinet with a 2080 Ti): `AAFactor` supersampling 1.25, standard FXAA, static ambient occlusion, static and ball reflections, bloom kept;
- **standard**: 6 GB or more, or a laptop (the development PC, 8 GB Quadro RTX 4000): `AAFactor` 1, fast FXAA, no ambient occlusion nor bloom, static reflections;
- **prudent** (cautious): less than 6 GB, or unknown card: like standard, ball reflections only.
All of them turn off MSAA (at least 4 samples in VPX, too costly at headset resolution), screen-space reflections (`SSRefl`) and motion blur.
The profile is only written in the VR INI's empty keys: a setting chosen by the player wins.
`[PlayerVR] ResFactor` is never written: VPX 10.8.1 compares the requested resolution with a texture limit read before its renderer starts, and always falls back to the headset's recommended resolution ("Requested resolution exceed the GPU capability" in VPX's log).
Rendering resolution is therefore set in the Oculus application (below).

**Sound in the headset** (test of 10 November 2026: the sound stayed on the PC, never in the headset's earphones).
Cyber Pinball looks for the headset's audio output among Windows' outputs, on general criteria (`headsetAudioOutput`: runtimes and headset brands in the output's name, Link's "Virtual Audio Device" first; never the "Steam Streaming" outputs nor the PC's).
As long as the menu is in the headset, the menu music, interface sounds and the Juke-box play on it (`menuOutput`); in a game in the headset, VPX too, the table's and the backglass's sound (ROM, PuP, music), through the game's INI (`[Player] SoundDevice` and `SoundDeviceBG`, `vrAudioSettings`).
Outside the headset, everything goes back to the configuration's output ("Son" step), the cabinet's INI never being touched.
Without a headset output (Link not plugged yet: it is searched for every 30 s), the sound stays on the configuration's output, and the log says so ("Son dans le casque : …").

**Link readings at every game in the headset** (`noteLinkStats`): at the end of the game, Link's statistics minute by minute, read from Oculus's performance log (`%LOCALAPPDATA%\Oculus\PerfLog_*.json`), are logged: frames presented, lost, shown again more than 5 times (VPX gave no new one), encode resolution; then the per-minute summary, with the worst minute and the profile applied ("Link, bilan de la partie (profil VR standard (8 Go de mémoire vidéo, portable, …))").
On 10 November 2026, before the profile: 541 frames shown again more than 5 times per minute on average, 733 in the worst minute, out of 4,320.
Aim for less than 50.

**Link settings, outside Cyber Pinball.**
Two places:
- **Meta Quest Link application** (on the PC) > Devices > the headset > Graphics preferences: **refresh rate** (72, 80, 90 Hz) and **render resolution** (the slider, which changes the recommended resolution VPX takes).
- **Oculus Debug Tool** (`C:\Program Files\Oculus\Support\oculus-diagnostics\OculusDebugTool.exe`, to reopen after each PC restart): **Encode Resolution Width** (Link's encode width: the sharpness the headset receives), **Encode Bitrate (Mbps)**, **Asynchronous Spacewarp** (ASW).
Recommended values, to check against the Link summary:
- **puissant** (cabinet, 2080 Ti): 80 Hz if the summary stays below 50 frames shown again per minute (otherwise 72 Hz); render resolution 1.2×; encode width 3,664; bitrate 300 Mbit/s over a USB 3 cable (200 over Air Link); ASW "Auto".
- **standard** (laptop, Quadro RTX 4000): 72 Hz; render resolution 1.0×; encode width 2,784 (2,304 by default on this machine, 1,152 dots wide per eye: the sharpness ceiling of the test); bitrate 200 Mbit/s over a cable (150 over Air Link); ASW "Auto".
- **prudent**: 72 Hz; render resolution 0.9×; default encode width and bitrate; ASW "Auto".
  `cyberpinball-casque.exe --diagnostic` lists each graphics card, its screens and what their duplication gives, without showing anything in the headset.

The detail of the "Réalité virtuelle" (Virtual reality) entry says where it stands: "menu de Cyber Pinball dans le casque" (Cyber Pinball menu in the headset), "menu dans le casque dès qu'il est prêt" (menu in the headset as soon as it is ready), or "compagnon absent de cette version" (companion missing from this version).

**Controllers: one rule, in the menu as in game** (`packages/core/src/manettes.ts`, `headsetControls`, pinned by [manettes.test.ts](../../packages/core/src/test/manettes.test.ts)).
A = confirm, always; B = back or cancel, always; the thumbsticks (both) move the selection, repeated while held; the triggers are the flippers in game, previous and next in the menu (like the cabinet flippers, repeated too); the grips are the MagnaSaves, in game only; X goes to the next collection in the menu (like the cabinet's right MagnaSave on the wheel; elsewhere, between the list and its actions), the credit in game; ≡ on the left controller opens the headset menu (in the Cyber Pinball menu) or the VPX menu (in game).
In the menu, the companion reads the OpenXR actions (`oculus/touch_controller` profile) on every frame while the menu has the player's gaze, and sends "bouton <nom> 1|0" on every change: `start`, `exit`, `menu`, `collection` (X), the triggers, and the directions of both thumbsticks (`haut`, `bas`, `gauche`, `droite`: the dominant axis, pressed beyond 0.6, released below 0.4).
Cyber Pinball hands them to the menu through the path of the cabinet buttons (`HEADSET_BUTTONS`, `headsetButton`, `headsetKey` in `app/src/frontend.ts`).
Headset taken off, Meta menu open or game launched, nothing arrives any more, and any held button is released.
**In game**, VPX 10.8.1's OpenXR bindings apply (`XRInputHandler.h`), and its defaults did not follow this rule: B gave a credit, X opened the VPX menu, and the left thumbstick click aligned the table on the controllers, continuously (`VRControllerCalibration`, `m_controllerViewCentering`: the table then follows the middle of the two controllers, at their height).
So the INI of every game in the headset receives the rule's bindings (`vpxHeadsetInput`, `VPX_HEADSET_MAPPINGS`): A = Start, and "increase / confirm" in the VPX menu (`UIRight`); ≡ = the VPX menu, and back in that menu (`InGameUI`); B = pause and resume (`Pause`: the VPX menu, stuck to the eyes in VR, no longer opens by accident, decision of 10 November 2026); thumbsticks = up, down, left, right in that menu (the left one also nudges the table, the right one pulled back cocks the plunger, as by default); triggers = flippers (staged at half travel); grips = MagnaSave; X = credit; Y = launch the ball; both thumbstick clicks, pressed together 3 s = align the cabinet, in the menu as in a game (nothing else).
Each action keeps its keyboard keys and cabinet buttons; VPX's automatic layout is turned off for the controllers (`[Input] Device.OpenXR.NoAutoLayout = 1`), otherwise it would put all its bindings back as soon as one is missing (`InputManager::SetDeviceDefaultMapping`); the plunger and nudging on the thumbsticks are added as sensors if they are not there (`PlungerSensorCount`, `NudgeSensorCount`).
The headset menu shows this legend, for the menu and for the game.
**Controllers wizard** (for every headset and every configuration): the companion reads each button and axis of the catalogue (`CONTROLLER_ELEMENTS`: triggers, grips, A, B, X, Y, left and right ≡, thumbstick and trackpad clicks, thumbsticks, trackpads), bound for each OpenXR interaction profile that has it (Quest Touch, Valve Index, HTC Vive, Windows Mixed Reality), and reports the profile plugged in ("profil touch").
Each profile has its default setting (`defaultControllerSetting`); the Touch one is the rule above.
The first time a headset without a setting for the active configuration is worn, the wizard opens by itself (before alignment): the buttons suggested for these controllers, then confirm to keep them, or back to set them one by one, like the cabinet's "Lanceur" (Plunger) step.
**Pause, and the only way out of a game** (test of 10 November 2026: Y quit too easily, and a setting without an exit trapped the player).
"Retour, Pause" (Back, Pause) is the wizard's required function, for every headset; "Quitter la partie" (Quit the game) is optional, and no default setting gives it.
While a game loads in the headset, the backglass says in large type "B : pause · tenu : quitter" (B: pause · hold: quit; the button of the setting).
**In the game, the VPX plugin "CyberPinball"** (`packages/vpx-vision3d/src/cyberpinball.cpp`, logic in `pause.h`, installed in `<VPX>\plugins\cyberpinball` like Vision 3D, `app/src/pause-vr.ts`): a short press on Pause, VPX pauses itself; the plugin notices (VPX's game time, `GetGameTime`, has not moved for 0.15 s) and shows "PAUSE", "REPRENDRE" / "QUITTER" (RESUME / QUIT), the current choice in green in a frame, and below, in large type, the keys reminder with the setting's real buttons ("JOYSTICK : CHOISIR" then "A : VALIDER", Stick: choose, A: confirm; `[Plugin.CyberPinball] Help`, one line per piece split by "·").
The stick (up "Reprendre", down "Quitter": VPX's `UIUp` / `UIDown` actions), the flippers or the MagnaSave choose; confirm (Start) confirms; Pause again also resumes.
"Reprendre" sends VPX's Pause key (P) to its window (VPX reads the keyboard of all its windows in VR), then, with no effect after 0.5 s, the same key through `SendInput` if VPX has the foreground; still no effect, the menu says so ("B : REPRENDRE", B: resume, `ResumeHint`).
A press held **1.5 s** (`QUIT_HOLD_S`), the game quits: a circle of 48 strokes fills in green around "QUITTER" (it appears after 0.2 s, not to flicker on a short press), releasing earlier cancels.
**Quitting is guaranteed**: the `ExitGame` action (like Escape: the table's script sees it), then, if the game still runs 0.8 s later, closing VPX's windows (`WM_CLOSE`, `SDL_EVENT_WINDOW_CLOSE_REQUESTED`: the game stops whatever menu is open), asked again as long as it runs.
**What the plugin never holds back** (test of 10 November 2026: a stuck game, neither Pause nor Escape answered, the player had to close Cyber Pinball).
Cause: `OnActionChanged` gives the plugin the action's **internal** number (`InputManager`, creation order), not the API's `VPXAction` enumeration; the plugin mixed them up: 15, "Pause" for it, is the credit in VPX, so the credit opened its menu, the real Pause (22) and the real exit (24) were then swallowed, and its attempt to pause VPX failed ("A plugin requested to set state of undefined action #15": VPX does not let a plugin inject Pause).
The watchdog saw nothing: VPX was not frozen, it drew, only its exits were held back.
Fix of the class: a table of VPX 10.8.1's internal numbers (`commandeVpx1081`, `pause.h`), checked during the game on every action VPX binds to the API (its state read by `GetInputState` must be the announced one); on a mismatch, or with another VPX version than 10.8.1, the plugin goes passive and swallows nothing.
And a single rule to swallow an action (`Pause::avaler`): never Pause, the exit (Escape, `ExitGame`), VPX's menu or an unknown action; the rest only during its menu, and nothing once quitting is asked.
VPX's menu open (≡): Cyber Pinball's pause steps aside.
On Cyber Pinball's side, during a game in the headset, **Escape on the keyboard** is taken by the application (global shortcut) and closes VPX, whether it has the keyboard or not; Ctrl+Shift+K stays the forced stop of any game.
Invariants fixed by [sortie-garantie.test.ts](../../packages/core/src/test/sortie-garantie.test.ts) (with any controller setting of every headset, Escape stays bound to VPX's exit and Pause has a button; the plugin never swallows Pause, the exit or VPX's menu) and by the pause bench.
**Framed backglass** (same test: the backglass content distorted).
VPX draws an ancillary renderer over the flasher's whole surface, whatever its shape: its backglass in VR is 4:3 (1.2 × the table's width), and B2S stretched its image there, PuP its root screen (laid over the whole surface, `PUPManager::Render`).
Outside the pause, the plugin, first among the backglass renderers, draws the next renderer itself through an intermediate context (`dessinerCadre`): what the renderer draws in its own surface is laid in the backglass with its proportions kept, centred (`cadrer`, `pause.h`), the bands staying on the flasher's black background.
The renderers' order is given by Cyber Pinball (`[Plugin.CyberPinball] Order`, from the `[Backglass] Priority.*` priorities, at equal priority B2S then PuP as VPX loads them, without those cut by a negative priority); PuP not knowing its shape, its backglass's shape is given to it (`PupRatio`, 16:9 by default).
The pause, drawn in a 4:3 frame of 1000 × 750, texts reduced to 940 wide, fits whole in this backglass.
**Visible part of the backglass** (test 0.1.9-essai.50, *The Matrix*: "backglass still cut at half its height"; the proportions had nothing to do with it).

**Probe that recovers on its own, outline of the current connection** (real test of 13 November 2026, 23:35-23:48): Link cut and back, the probe's old LibOVR session no longer saw the headset ("casque=0", one input error -3003), the probe stayed silent for a whole session, and anchoring moved the cabinet by 121 cm on an outline read in a past connection, which the next alignment even attached to the place.
Now: the probe recreates its session from scratch (`ovr_Shutdown`, `ovr_Initialize`, `ovr_Create`) when the status or the inputs answer a service error (-3000 to -3999), when the display is lost, or when the headset has been absent for it for 10 s ("ovr session refaite raison=…", said when the reason changes); it writes a pulse every second ("ovr pouls casque=0|1 porte=0|1", kept out of the log).
It exits on its own 3 s after the requested end or after its input closes (Cyber Pinball gone): a call stuck in LibOVR never leaves it orphaned.
On the application side, a guard (`OvrProbe.check`): companion ready and the probe silent or without the headset for 5 s (`PROBE_GUARD_MS`), it is restarted, at most once every 30 s, with a line in the log.
The outline is only usable when read during a companion session in which the probe followed the headset without a break (`RoomFrame.companionSession`, `probeLost`, `bloque` state): the probe loses the headset, the outline is forgotten and the log says no jump can be measured; at each companion session ("pret"), the kept outline waits to be read again (the probe says it again, "contour" command); probe not following at that moment, nothing is read before a followed session (the probe finding the headset again at the menu, the companion is restarted once to read it).
Meanwhile, no anchoring and no outline attached to a place: when aligning, the place has no outline, and the "Calez la borne une fois" notice will say so.
On the bench: `link 0|1` verbs (Link cut, earlier sessions in error -3003, then back), `sonde-perimee` (casque=0 with no error), `sonde-gelee` (the probe no longer answers); the probe recreates its session and reads the outline of the new frame (cabinet put back within 2 cm and 1°), the guard restarts a frozen probe (not when the companion does not have the headset), and 23:39 replayed: anchoring refused, nothing attached, then the cabinet put back right.
**VPX's table kept in place during a game: the frame layer** (real test of 13 November 2026, 23:50-23:52: three origin resets during a game, measured, place and INI rewritten, but VPX 10.8.1 reads nothing again and the table stayed wrong in the headset until the next game).
Trial a) showed that the origin given back by the probe only holds for it: the correction is therefore made inside VPX itself, by an OpenXR API layer (`packages/casque-vr/src/couche-repere.cpp`, `XR_APILAYER_CYBERPINBALL_repere`), loaded in VPX's process only: Cyber Pinball sets `XR_API_LAYER_PATH`, `XR_ENABLE_API_LAYERS` (ahead of those already requested) and `CYBERPINBALL_REPERE` at launch (`roomLayerEnv`, `launchVpx`); nothing is installed for the computer.
VPX creates a single room space (STAGE), in which it places its table from its INI and locates its views, its projection and its controllers.
The layer gives it, in its place, a STAGE space corrected by the composition of the jumps measured since its launch (pose of the old frame in the new one: rotation of −angle around the vertical, then translation and floor), substituted in `xrLocateViews`, `xrLocateSpace`, `xrLocateSpaces` and the `xrEndFrame` layers; the correction is taken at the start of each frame (`xrWaitFrame`) and held for the whole frame.
On the application side (`app/src/couche-repere.ts`, `GameRoom`): at each game in the headset, the place read by VPX and a zero correction (`<data>\vr\correction-partie.txt`, written in one go); at each jump measured during the game, the composition rewritten (three jumps in a row compose); the base INI keeps being rewritten for the next game, which starts again from a zero correction (no double correction).
After the game, the layer's log (`couche-repere.txt`) is copied into the log ("Casque, couche du repère : …"); an alignment made during the game is expressed in VPX's corrected frame: it is read against the launch place and carried by the jumps the layer applied (`checkVrPlaceAfterGame`).
Layer missing, refused or without effect: VPX starts as before, said in the log.
Bench proof (`scripts\banc-vpx.ps1 -Repere 1`, real VPX 10.8.1 on the fake runtime, real probe): three origin resets during a game (170.7°, −29.8°, −48.1°), VPX's projection space back within 0.01 cm and 0.00° of its starting place in the world after each (two wrong frames at most), and the resting controllers seen by VPX at the alignment gesture, after the three resets, at their launch place; `-Couche 0` replays the same game without it.
**Nothing concluded from a session in error; a single truth for the Link transport** (real test of 13 November 2026).
At 23:26, "pièce du Quest sans limite" then "calage périmé, Quest maintenant en limite fixe" had been concluded from a dying session (one eye's image refused, unreadable outline, lost 13 s later): the boundary had not changed.
Now "piece aucune" is no longer judged at "pret" but when the headset is put on, in the same session, with no scene or OpenXR error in between (`stationaryVerdict`); session in error or lost before: "rien n'est conclu, type de limite inchangé".

The cabinet's aligned place kept nothing of it.
Link transport: "par câble USB" at 23:39 then "Air Link sur un PC en Wi-Fi" at 23:50, in the same session.
The transport came from the last record of Oculus's performance log, whatever its time, and from the mere presence of the headset's Wi-Fi (on with the cable too).
Now: the record's `transmission_type` field first ("USB": cable), the Wi-Fi only when it is missing (`blockTransport`, the same for the whole application), and only the records of the current connection (`linkTransportSince`, since the first "pret" after a lost headset or a probe without the headset); with no record, the transport stays unknown and the "Air Link" warning is not given.
The log says the time of the record used.
The cause, read in the cabinet's real performance log (Air Link, PC on Wi-Fi according to the player): the first record of each connection (23:39:18, 23:48:14) is a 20-field opening, "TCP" but no Wi-Fi yet; read by the Wi-Fi alone, it gave "USB cable"; the next record, with the Wi-Fi, gave Air Link (23:50).

**The layer set aside if VPX falls with it** ("VPX crash: faulty module" rule): a game in the headset launched with the layer and ended abnormally (VPX crashed, error exit code, or end within the first 10 s of play with no stop asked by Cyber Pinball, `roomLayerFault`) says so in the log naming the layer, and the next games start without it until the next update (`<data>\vr\couche-repere-ecartee.json`, lifted when the version changes), with no option on screen.

### 3D vision

System menu > "Borne" (Cabinet) > "Vision 3D" (3D vision) (`app/src/vision3d.ts`, rules in `packages/core/src/vision3d.ts`): the table perspective follows the player's head, like a window opened onto the playfield ("head tracking").
Off by default, Start toggles it; "BETA" badge.
The setting is kept in `<données>\vision3d\reglage.json`, with the head's playing position for each cabinet configuration.

Sensors, recognised among the USB devices present without opening anything (`vision3dHardware`; the "Camera" or "Image" driver class is read by `packages/win-displays/src/usb.ts`):

- a Kinect for Xbox 360 (VID 045E), plugged in with its power adapter, comes first.
  Without its driver (`Kinect10.dll` in System32) or, for a Kinect for Xbox 360 (camera 045E:02AE), without SDK 1.8 registered (`HKLM\SOFTWARE\Microsoft\Kinect` `SDKInstallPath`, or `KINECTSDK10_DIR`), the entry becomes "pilote Kinect à installer" (Kinect driver to install).
  The driver alone (runtime) indeed refuses a Kinect for Xbox 360 (`NuiInitialize`: `E_NUI_NOTSUPPORTED`, 0x83010008); only the Kinect for Windows makes do with it.
  Choosing it downloads from Microsoft the SDK 1.8 installer, which also holds the drivers and runtime (`kinect-sdk-1.8` component in `packages/installer/components.json`, `on-demand` distribution, SHA-256 checked), checks its Authenticode signature (exact Microsoft Corporation subject, `signer` field).
  The installer itself is never run: its interface ("RedistUX", .NET) shows its licence checkbox despite `/quiet`, and a full-screen menu covers it.
  Its packages (`bundlePackages`: Visual C++ x64, x64 drivers, runtime and SDK, with the SDK's external `redist.cab` archive placed next to it) are taken from its attached archive (the largest CAB archive in the file, `attachedCabinet`) by Windows' `expand.exe`, each checked as signed by Microsoft, then installed without any window (`msiexec /qn`) by an elevated script: Windows asks for consent once.
  The entry says that installing means accepting Microsoft's licence.
  Once the driver is in, 3D vision turns on.
  Cyber Pinball never ships it.
  The 2013 driver (`kinectcamera.sys`) is refused by Windows 11 memory integrity (Windows Security > Device security > Core isolation; read from `HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard\Scenarios\HypervisorEnforcedCodeIntegrity`, `packages/win-displays/src/device-guard.ts`).
  When it is on, the installation is not offered; a plugged-in webcam takes the Kinect's place (the detail says so), otherwise the "Kinect bloquée par Windows" (Kinect blocked by Windows) entry frees the screens and opens the "Core isolation" page.
  Cyber Pinball never changes this security setting: the player decides.
  A driver failure is stated in plain words from its code (`nuiErrorReason`, codes from `NuiApi.h`): Kinect not supported without the SDK, no power, already in use, not enough USB bandwidth…;
- otherwise, a webcam.
  A window that is never shown (`renderer/vision3d-webcam.html`, `vision3d` partition) opens the camera alone (no microphone) and finds the face in every frame with MediaPipe Tasks Vision (full-range BlazeFace, `app/ressources/vision3d/blaze_face_full_range.tflite`, on the CPU).
  The short-range model does not find a face that fills only a tenth of the picture, which is what it does in front of a cabinet, more than a metre away.
  Frames are read through `MediaStreamTrackProcessor`: a hidden window may stop decoding a video.
  The distance comes from the gap between the eyes (6.3 cm) and the camera's field of view (70° by default, `webcamFovDeg`).
  This window has no network access: pictures never leave the PC;
- a Kinect for Xbox One is recognised, but not supported yet: the entry says so.

Without a sensor, the entry stays visible, greyed out with the reason.
An application built without the C++ tools has no plugin: the entry says so too.

The entry opens the "Vision 3D" (3D vision) screen (`openVision3dScreen`, `app/src/frontend.ts`): where the sensor stands, in plain words, then "Activer" or "Désactiver" (Turn on or off), "Tester le capteur" (Test the sensor), "Installer" or "Réinstaller le pilote de la Kinect" (Install or Reinstall the Kinect driver), "Ouvrir « Isolation du noyau »" (Open "Core isolation").
The Kinect state is read from Windows without opening it: its camera (PID 02AE or 02BF) only shows up when powered by the power adapter ("Kinect sans courant" (Kinect without power)), and its driver state comes from the configuration manager (`deviceStatus`, `packages/win-displays/src/usb.ts`: driver loaded, otherwise the Device Manager code; 28: no driver, to install; any other code: driver present but not loaded, restart needed, for instance right after turning memory integrity off).
A Kinect that is not ready gives way to a plugged-in webcam, and the detail says why.
"Tester le capteur" (Test the sensor) turns it on outside a game for 20 s (`HeadTracker.test`): the screen shows the head's distance and offset live, nothing is sent to VPX nor saved; the test stops by itself, on going back, or when a table starts.
After each game with 3D vision, a report is written to the log and shown on the screen (`vision3dGameReport`): what `vpinball.log` says about the plugin since the launch ("Plugin Vision3D loaded", "was found but is disabled", a load failure, or nothing: `vision3dPluginLog`), the number of positions sent, the delay between the table on screen and the first tracked head ("dès le début" (from the start), or "N s après le début" (N s after the start)) and the sensor failure if there was one.
It tells where to look when the view does not move, or is slow to move.

Three settings, on the "Vision 3D" (3D vision) screen, kept in `reglage.json` and applied at once to the running sensor (`HeadTracker.configure`):

- "Calibrer la position de jeu" (Calibrate the playing position): the sensor on (test), 50 measurements, about two seconds, the player still in playing position; their median becomes the playing position of the cabinet configuration.
  Safer than the measurement taken on the fly at the start of a game;
- "Intensité" (Intensity) (`intensity`, 25 % to 150 %, 75 % by default): the head shift is multiplied by it before being sent to the plugin.
  At 100 %, the table moves as behind a real window; lower, it moves less, against "seasickness".
  Also adjustable in game: the MagnaSave buttons, then "Intensité de la vue 3D" (3D view intensity), each Start moves to the next one;
- "Réactivité" (Responsiveness) (`smoothing`, `SMOOTHING_PRESETS`): the "1 €" filter and an anticipation from the head's speed (4 cm at most), which hides part of the sensor's lag (the Kinect measures 30 times a second and delivers the head 60 to 100 ms late).
  Gentle: 0.7 Hz, 0.05, no anticipation (the previous setting, about 45 ms of lag added by smoothing on a clear movement); normal: 1 Hz, 0.3, 35 ms (about 12 ms); quick: 1.5 Hz, 0.8, 60 ms (almost nothing).

For a game (not "Régler l'affichage en partie" (Adjust display in game), not a game in the headset), the sensor turns on as soon as Start is pressed, while the table loads (`HeadTracker.warm`): nothing is sent to VPX before the table is on screen (`HeadTracker.start`).
In seated mode, the Kinect only picks up a player who moves (SDK 1.8 documentation); turned on once the player stood still in front of the playfield, it took long seconds (PinCab log, 13/11/2026: 13 to 39 s of game without tracking).
At the end of the game, the sensor stays on for two minutes (`HeadTracker.release`, `VISION3D_KEEP_WARM_MS`): the next game takes it over, player already picked up, then it turns off by itself; turning 3D vision off or starting a game in the headset turns it off at once.
`NuiInitialize` (half a second to a second) and the driver shutdown run on a koffi thread, one after the other (`nuiAsync`): the loading screen does not freeze.
The log says when the head was picked up after the sensor turned on, and tracked after the game started.
Kinect: `Kinect10.dll` is read through koffi, skeleton in seated mode (the upper body is enough behind the cabinet body), "head" joint of the first tracked skeleton, levelled from the floor the sensor sees (`kinectHead`).
Once per power-on, the Kinect motor aims at the head if it is more than 6° off centre (`kinectAim`); the frames that follow, while it turns, are ignored.
The position is smoothed ("1 €" filter, `OneEuroFilter`), compared with the playing position, capped at 60 cm, then sent to the VPX plugin over local UDP (127.0.0.1, port 4242, opentrack format: six doubles, x, y, z in centimetres).
The playing position is the median of the first 24 measurements, saved for the cabinet configuration; "Recentrer la vue 3D" (Recenter the 3D view), in the in-game settings (MagnaSave), measures it again.

The "Vision3D" VPX plugin (`packages/vpx-vision3d`, C++) is copied into `plugins\vision3d` of the active VPX version before each game if it changed, and enabled like the other plugins (`enabledPlugins` in the manifest).
It stays inert as long as it receives nothing: a game without 3D vision pays nothing for it.
On the first packet, it turns off VPX's static pre-render (the scenery must follow the head), then, on every frame (`OnPrepareFrame`), moves the point of view (`SetActiveViewSetup`, `viewX`, `viewY`, `viewZ`).
In "Window" mode (cabinet, `ViewCabMode` = 2), the shift gets the same rotation VPX applies to the player position (`ViewSetup::SetViewPosFromPlayerPosition`): the perspective is that of a real window.
In "Camera" mode (desktop), the camera follows the head, an approximate effect.
Adjustable gain (`[Plugin.Vision3D] Gain`, 1 = real movement).
Silent sensor: gradual return to the neutral view within a second.
At the end of the game: original view and pre-render restored.
The opentrack format also lets opentrack itself plug in (its axis directions are set in opentrack).
Build: `node scripts/vision3d.mjs` (with `--banc`: test bench without VPX); `npm run deployer` does it too when CMake and the Visual Studio 2022 C++ tools are there.

Limits: the effect only works for the tracked player, and a camera filming the screen does not show it; the webcam needs some light; the Kinect for Xbox One is not supported.
Tests: `packages/core/src/test/vision3d.test.ts`, `vision3d-webcam.test.ts` (Chromium fake camera and test portrait), `vision3d-kinect.test.ts` (fake `Kinect10.dll`, `packages/vpx-vision3d/test/kinect-factice.cpp`), plugin bench (`packages/vpx-vision3d/test/banc.cpp`).
